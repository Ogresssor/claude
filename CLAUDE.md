# CLAUDE.md — правила для разработки сайтов

Этот файл Claude читает в начале каждой сессии. Отвечай пользователю **на русском**.
Цель каждого проекта: современный, технологичный, быстрый и **безопасный** сайт, который не стыдно показать.

---

## 1. Стек по умолчанию

Если пользователь не попросил другое, используй:

| Задача | Выбор |
|---|---|
| Фреймворк | **Next.js** (App Router, Server Components) + **TypeScript** (`strict: true`) |
| Стили | **Tailwind CSS** + CSS-переменные для цветов и тем |
| UI-компоненты | **shadcn/ui** (Radix под капотом, доступность из коробки) |
| Анимации | **Motion** (бывший Framer Motion); для сложного скролла — **GSAP + ScrollTrigger**, плавный скролл — **Lenis** |
| 3D и WebGL | **React Three Fiber / drei** или **Spline**, только если 3D действительно нужно |
| Иконки | **lucide-react** |
| Шрифты | `next/font` (Geist, Inter, Manrope и другие), без внешних запросов к Google Fonts |
| Формы и валидация | **react-hook-form + zod** |
| Данные и авторизация | Server Actions / Route Handlers; БД и авторизация — **Supabase** (с RLS) или **Auth.js** |
| Деплой | **Vercel** (или Cloudflare) |
| Простой лендинг без логики | можно **Astro** + Tailwind |

Правила выбора:
- Ставь **актуальные стабильные версии** пакетов и сверяйся с их документацией, а не с памятью.
- Не добавляй зависимость, если задачу закрывают 20 строк своего кода.
- Перед добавлением пакета проверь, что он живой: недавние релизы, нормальное число загрузок, без известных уязвимостей.

## 2. Дизайн: уровень «premium / tech»

Ориентир — [horizonx.so/explore](https://horizonx.so/explore). Что там на самом деле (по каталогу, октябрь 2026):
- **Кинематографичные лендинги со скролл-сторителлингом**: сцены сменяются по скроллу, история продукта рассказывается «главами» (Lotus Perfume, Alder & Stone, Vigil, ARQ-01 — на секвенции кадров 24 fps).
- **Живой WebGL / Three.js в hero**: частицы, которые реагируют на курсор (Sorvine, Orvane — 150 000 частиц, MORPHO), 3D-объекты над водой с отражениями (Crest Water), огонь и вода в реальном времени (Emberline, Aurel Liquid), тоннель из картинок, который тянется мышью (Yohaku), 3D-скан города из точек.
- **Hero-формула**: заголовок по центру, одна строка описания, **две кнопки CTA**, а под ними — дашборд продукта или 3D-сцена, «вырастающая» из визуала.
- **Liquid glass**: полупрозрачные слои с blur и светящимися краями, «стеклянная» плавающая навигация.
- **Bento-сетки** с живыми данными: метрики, графики, gauge, карточки уведомлений, один яркий акцент (лайм, оранжевый, бирюзовый, фиолетовый).
- **Тёмные дашборды** (CRM, трейдинг, AI-ассистент) и editorial-лендинги со своей палитрой (пергамент + полночь, вино, архитектура).
- **Интерактивные симуляторы и конфигураторы** в 3D (голограммы, протез руки).

**Визуальный язык**
- Тёмная тема по умолчанию (почти чёрный `#0a0a0a`–`#0b0b0f`, не чистый `#000`) плюс аккуратная светлая тема.
- Крупная выразительная типографика: заголовки 56–96px на десктопе, плотный трекинг (`tracking-tight`), контрастные начертания.
- **Bento-сетки** для фич, карточки с тонкими границами (`border-white/10`) и мягкими тенями.
- Градиенты и свечение: радиальные «glow»-пятна за ключевыми блоками, градиентный текст в акцентах (умеренно).
- **Glassmorphism** точечно: `backdrop-blur` у навбара и модалок.
- Фоновые детали: сетка или точки с маской затухания, шум (noise), тонкие линии.
- Один акцентный цвет плюс нейтральная палитра; без «радуги».
- Много воздуха: секции с отступами 96–160px, чёткий вертикальный ритм.

**Движение**
- Плавное появление при скролле (fade + сдвиг 8–24px, 0.4–0.8s, easing `easeOut`).
- Микровзаимодействия: hover на кнопках и карточках, магнитные кнопки, spotlight-курсор на карточках.
- Бегущие строки логотипов, анимированные счётчики, параллакс — к месту, без перегруза.
- Для «вау»-hero: WebGL-сцена (Three.js / R3F, шейдеры), реакция на курсор, скролл-сцены через GSAP ScrollTrigger или секвенция кадров на `<canvas>`.
- 3D и WebGL обязательно с **фолбэком**: статичная картинка или видео-постер на слабых устройствах, при `prefers-reduced-motion` и без WebGL; сцена грузится лениво и не блокирует первый экран.
- **Обязательно** учитывай `prefers-reduced-motion`: при нём анимации отключаются или упрощаются.
- Анимируй только `transform` и `opacity`. Никаких анимаций `width`, `top` и прочих свойств, вызывающих перерасчёт раскладки.

**Типовая структура лендинга**
Navbar (sticky, blur) → Hero (сильный заголовок, подзаголовок, 2 CTA, визуал или 3D) → логотипы и соцдоказательство → bento с фичами → «как это работает» → отзывы → тарифы → FAQ → финальный CTA → футер.

**Чего избегать**
- Шаблонный «AI-вид»: фиолетовый градиент везде, эмодзи вместо иконок, одинаковые карточки.
- Lorem ipsum в финальной версии: пиши правдоподобный текст по теме проекта.
- Стоковые картинки низкого качества; лучше абстрактная графика, SVG или 3D.

## 3. Качество — критерии «готово»

Сайт не считается готовым, пока не выполнено всё ниже:
- **Адаптив**: идеально от 360px до 1920px+, без горизонтального скролла на телефоне.
- **Производительность**: Lighthouse ≥ 90 по всем категориям; LCP < 2.5s, CLS < 0.1, INP < 200ms.
  - Картинки через `next/image` (AVIF/WebP, `sizes`, `priority` только у hero).
  - Тяжёлое (3D, карусели) — через `dynamic import` и lazy load.
- **Доступность (WCAG AA)**: семантичный HTML, контраст ≥ 4.5:1, видимый `focus`, `alt` у картинок, навигация с клавиатуры, `aria-*` где нужно.
- **SEO**: `metadata` на каждой странице, Open Graph и Twitter-карточки, `sitemap.xml`, `robots.txt`, favicon и иконки, один `h1` на странице.
- **Код**: без `any`, без закомментированного мусора, компоненты небольшие и переиспользуемые.
- Перед тем как сказать «готово», запусти: `lint`, `typecheck` (`tsc --noEmit`), `build`, тесты (если есть). Сообщай честно, если что-то упало.
- По возможности проверяй результат в браузере (Playwright, скриншоты на мобильной и десктопной ширине).

## 4. Безопасность (обязательно в каждом проекте)

**Секреты**
- Никогда не коммить ключи, токены и пароли. Только `.env.local`, в репо — `.env.example` с пустыми значениями.
- `.gitignore` с самого начала: `.env*` (кроме `.env.example`), `node_modules`, `.next`, `.vercel`.
- В Next.js переменные с `NEXT_PUBLIC_` попадают в браузер: туда **только** публичные значения.
- Если секрет случайно утёк в коммит, считай его скомпрометированным: отозвать и перевыпустить, а не просто удалить из истории.

**Ввод и данные**
- Любой ввод пользователя валидируй **на сервере** (zod), даже если проверка есть на клиенте.
- Не используй `dangerouslySetInnerHTML` с пользовательскими данными; если без HTML никак — санитайзинг (DOMPurify).
- SQL только через параметризованные запросы или ORM, никакой конкатенации строк.
- Загрузка файлов: проверка типа и размера, хранение вне публичной папки или в объектном хранилище.

**Авторизация**
- Проверка прав — на сервере, в каждом Server Action и Route Handler, а не только скрытием кнопки в UI.
- Supabase: **RLS включён на всех таблицах**, `service_role`-ключ только на сервере.
- Cookies сессии: `HttpOnly`, `Secure`, `SameSite=Lax` (или `Strict`).
- Rate limiting на формы, логин и API (например, Upstash Ratelimit); защита форм от спама (honeypot / Turnstile).

**Заголовки и инфраструктура**
- Настрой security headers: `Content-Security-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`, `frame-ancestors` (или `X-Frame-Options`).
- Только HTTPS. Внешние ссылки с `target="_blank"` — с `rel="noopener noreferrer"`.
- Сообщения об ошибках пользователю — без стектрейсов и внутренних деталей.

**Зависимости**
- Регулярно `npm audit` (или `pnpm audit`), lock-файл всегда в репо.
- Не ставь подозрительные и малоизвестные пакеты; следи за опечатками в названиях (typosquatting).
- Включи Dependabot / Renovate и GitHub secret scanning.

Если задача пользователя требует ослабить безопасность (например, отключить проверку), сначала предупреди о риске и предложи безопасную альтернативу.

## 5. Код-ревью (по статье Anthropic)

Источник: [«How the Claude Code team does code review»](https://claude.dev/blog/solving-code-review-at-anthropic/), Addy Osmani, Morgan Westlee Lunt, Qing Wang, 15 октября 2026.

### Главное из статьи
- Claude пишет около 90% кода Claude Code. С июня по сентябрь число смёрженных PR выросло больше чем вдвое, а доля откатов упала больше чем на 40%. Ревью не убрали: основное чтение кода передали машинам и вложились в быструю отмену ошибок.
- У ревью две задачи: **найти и исправить проблемы до релиза** и **дать команде общее понимание кода**.
- Вопрос «читал ли человек код?» — неточная замена вопросу «что может сломаться в этом изменении и какая проверка, автоматическая или человеческая, это поймает?».
- Ревью идёт **непрерывно, как проверка орфографии**, а не шлагбаумом в конце: большинство изменений Claude уже проверил и исправил хотя бы раз до того, как смотрит человек.
- Дефицитный ресурс — **время и внимание людей**. Цель: большинство PR мёржится максимум с одним человеком в цикле (им может быть сам автор) **без роста откатов и инцидентов**. Метрики: одобрения людей на PR, комментарии людей, время ожидания человека. Ограничитель — частота откатов и инцидентов: если она растёт, время не сэкономлено, а просто перенесено.

### Слои проверки (не один шлагбаум)
1. **Работа проверена до того, как на неё кто-то посмотрит.** Дай Claude то, что можно запустить (тесты, сборку, скриншот для сравнения с дизайном), и требуй **показать вывод**, а не сказать «готово». Затем субагент со **свежим контекстом** ревьюит diff. Перед PR — навыки: поиск багов, упрощение diff, проверка поведения end-to-end; UI сверяется с дизайн-гайдлайнами. Борис Черни: возможность проверить свою работу улучшает результат в 2–3 раза.
   - Если ревьюер повторяет одно и то же замечание — исправляй **у источника**: в скилле, правилом линтера или в инструкциях.
   - **CLAUDE.md** — что за проект: стек, соглашения, цели и не-цели. Короткий, ссылается на другие документы. Ревьюер отмечает код, нарушающий соглашения из него, и изменения, из-за которых строка в нём устарела.
   - **REVIEW.md** — что важно ревьюеру в этой части кода. Хороший REVIEW.md короткий: описывает, как выглядит провал в этом репо (для документации — «она врёт», для конфига — «он неправильно маршрутизирует»), ограничивает число nit, перечисляет пути, которые пропускать, требует **файл и строку как доказательство**, а не догадку по названию, и просит сводку, начинающуюся с количества находок и прямо говорящую, когда исправлять нечего.
2. **AI-ревью на каждый PR.** Читает diff в контексте всего репо и заявленной цели PR: решает ли изменение задачу, вписывается ли в систему, не ломает ли что-то ещё. Для багфикса ищет **корневую причину**. Несколько агентов ищут баги параллельно, отдельная группа **голосует** по каждой находке; публикуется только то, с чем согласно достаточно агентов. Находки только про стиль, диагностику или чистку отбрасываются. Комментарии сортируются по серьёзности с метками **Important / Nit / Pre-existing** (чтобы старый баг не выглядел виной автора). **На каждую находку нужен ответ**: исправить или закрыть тред с причиной. Режимы глубины: Quick / Standard / Deep; Deep — там, где пропущенный баг дороже времени ревью.
3. **Security-ревью, которое может заблокировать.** PR не мёржится, пока открыта хоть одна находка из ревью багов или безопасности. Ложное срабатывание закрывается коротким обоснованием; если поздний коммит исправил проблему, находка закрывается сама. Локально — `/security-review` или GitHub Action.
4. **Блокирующие автопроверки**: lint, типы, тесты на всех платформах, сборка. Шаблон PR спрашивает, **как изменение тестировали и как его откатить**; Claude может заполнить, но подписывает человек, попросивший изменение.
5. **Одобрение людей по уровню риска:**

   | Риск | Примеры | Одобрений людей |
   |---|---|---|
   | Низкий | Документация, тексты, внутренние фичи, добавления за флагом | Не нужно, если авторевью и security зелёные |
   | Средний | Обычные продуктовые изменения; чувствительные зоны: кэш, автообновление, системные промпты | Один человек |
   | Высокий | Самый рискованный код и пути, всегда требующие двоих | Два человека |

   - Уровень задаёт **изменение, а не автор** (его определяет классификатор). Пути, помеченные владельцами как чувствительные, и любые файлы CI-воркфлоу всегда требуют человека.
   - Облегчённый путь — только для доверенных авторов. **Одобрение агента никогда не засчитывается как человеческое.**
   - **Кто попросил агента написать изменение — тот за него отвечает** и считается одним из ревьюеров.
   - Одобрение относится к **конкретному коммиту**; новые непроверенные коммиты (пуш агента, ручной merge) требуют повторного одобрения.
6. **Merge queue, флаги, постепенный релиз.** Очередь перезапускает все проверки на main с изменением, чтобы два зелёных PR вместе не сломали main. Новое поведение — за флагом, сначала для своих, потом канал latest, затем stable.
7. **Быстрое обнаружение и откат.** Флаги выключаются без деплоя; разбор инцидента спрашивает, **какой слой должен был это поймать**. Лучше быстрее замечать и чинить, чем просто замедляться.

### Как улучшают ревьюера
- **Каждый инцидент — это eval**: прошлые PR, вызвавшие инциденты и откаты, с подтверждённым экспертами местом бага; ревьюер прогоняется по ним ежедневно, каждое изменение промптов, инструментов или модели оценивается заново.
- **Шум измеряется по реакции людей**: исправили / сказали, что неверно / поведение намеренное / неважно. Плюс прогон на заведомо чистых PR: как часто ревьюер толкает к вредному изменению. Приоритет: **сначала ловить реальные баги, потом сокращать число раундов**.
- Шум дороже, когда автор — агент: человек отмахнётся от nit за секунды, агент его исправит — новый коммит и новый раунд.
- **Ревью должно сходиться** (был PR с 50+ раундами за ночь; ~59% повторных замечаний — код, существовавший с первого прохода):
  - лимит **3 раунда**, затем ревьюер просит автора пересмотреть подход;
  - после первых проходов — **ревью только нового diff**;
  - отмечать **класс бага**, чтобы автор исправил все места, а не одну строку;
  - **не повторять** уже опубликованные находки.
- Агенты ревью ночью проходят и по существующему коду, чтобы ловить старые баги.

### Где остаются люди
- Решать, **стоит ли вообще это строить**: направление, вкус, объём.
- Ревьюить рискованный код: биллинг, автообновление, CI-воркфлоу.
- Ревьюить архитектуру, которую будут копировать.
- **Читать доказательства**: вывод тестов, команду и её результат, скриншот, находки ревьюера. Если не можешь сказать, что проверки пропустят, — нужно настоящее ревью, а не быстрое одобрение.
- **Отвечать за результат**: за каждое изменение отвечает человек, кто бы его ни напечатал.
- Понимание кода: вместо чтения тривиальных diff попроси Claude написать объяснение (или визуализацию) нужного куска кода.
- **«Ты смёржил — ты отвечаешь»**: изменения маленькие, всё откатываемо, планка зависит от радиуса поражения, регрессии видны быстро, это не поиск виноватых.
- Если идёт не туда — поднимай другое направление **рано**, а не блокирующим комментарием к готовому PR; закрыть быстро написанный PR не жалко.

### Как применять в моих проектах (рекомендации статьи)
**До PR**
- Короткий CLAUDE.md с командами проверки + хуки, запускающие форматтер и линтер.
- Локально `/code-review` и `/security-review` или ревью субагентом со свежим контекстом.
- Завести REVIEW.md и переносить туда повторяющиеся замечания.

**На каждом PR**
- Обязательный CI; в шаблоне PR разделы **«Testing»**, **«Risk»** и **«How to revert»**.
- AI-ревьюер (Code Review for Claude Code или Claude Code GitHub Action) сначала на одном репо, пару недель настраивать REVIEW.md, потом расширять.
- Автоматическое security-ревью; **все треды должны быть закрыты до мержа**.
- Глубина ревью по риску; лимит раундов, после первых — только новый diff.

**Одобрение**
- Записать уровни риска, задаваемые изменением, а не автором; начинать строго, ослаблять по фактам.
- Облегчённые пути — только для доверенных авторов.
- CODEOWNERS и branch protection: auth, биллинг, CI, релизные воркфлоу и инсталляторы всегда требуют человека.
- Одобрение бота никогда не заменяет обязательное человеческое; сбрасывать одобрения при новых коммитах.

**Мёрж и после**
- Merge queue, feature flags, сначала внутреннее использование, поэтапный релиз и откат в один шаг.
- Инциденты и откаты — в eval-набор; переоценивать ревьюера при любом изменении промптов, инструментов или модели.
- Измерять время людей, с частотой откатов и инцидентов как ограничителем.

> Когда ревью что-то пропустило — спроси, чего модели не хватило, и внеси исправление в CLAUDE.md, скилл или новую проверку.
