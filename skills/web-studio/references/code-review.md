# Код-ревью и самопроверка

Основано на статье [«How the Claude Code team does code review»](https://claude.dev/blog/solving-code-review-at-anthropic/) (Addy Osmani, Morgan Westlee Lunt, Qing Wang, 15 октября 2026).

## Идея статьи
- Код пишут агенты, поэтому дефицит — **время и внимание людей**. Цель: минимум человеческого времени на изменение **без роста откатов и инцидентов** (откаты и инциденты — ограничитель: если растут, время не сэкономлено, а перенесено).
- Правильный вопрос — не «читал ли человек код?», а «что может сломаться и какая проверка, автоматическая или человеческая, это поймает?».
- Ревью идёт **непрерывно, как проверка орфографии**, а не шлагбаумом в конце.

## Что делаю я (Claude) в каждом проекте

**1. Проверяю работу до того, как её увидит пользователь**
- Запускаю то, что можно запустить (lint, типы, сборка, тесты, скриншот против дизайна) и **показываю вывод**, а не пишу «готово». По словам Бориса Черни, возможность проверить работу улучшает результат в 2–3 раза.
- Делаю ревью diff «свежим взглядом» (по возможности — субагентом с чистым контекстом или `/code-review`).
- Для изменений в формах, авторизации, API, файлах, env — отдельный проход безопасности (`/security-review` и `security.md`).

**2. Каждую находку проверяю**
- Указываю **файл и строку** и реальный сценарий (вход → неверный результат или падение), а не догадку по названию.
- Находки только про стиль, диагностику или чистку не выдаю за баги.
- Метки серьёзности:
  - **Important** — реальный баг или уязвимость, исправить до мержа;
  - **Nit** — мелочь, не блокирует; число nit ограничиваю;
  - **Pre-existing** — проблема была до этого изменения, отмечаю, но это не вина автора.
- Сводку начинаю с количества находок; если исправлять нечего — говорю прямо.
- Для багфикса ищу **корневую причину**.

**3. Ревью должно сходиться**
- Не больше **3 раундов**; дальше — остановиться и предложить пересмотреть подход.
- После первых проходов — проверять **только новый diff**.
- Называть **класс бага**, чтобы исправить все места, а не одну строку.
- Не повторять уже озвученные находки.

**4. Исправляю у источника**
- Если одно и то же замечание повторяется — правило в CLAUDE.md / REVIEW.md, линтер или проверка, а не бесконечные правки.
- Когда баг всё же попал в прод — добавить тест на него и спросить, какой слой должен был его поймать.

## Слои проверки из статьи (для проектов с командой и CI)
1. Самопроверка до PR (запускаемые проверки + ревью со свежим контекстом).
2. AI-ревью на каждый PR: параллельные агенты ищут баги, другие голосуют по каждой находке; на каждую находку нужен ответ (исправить или закрыть с причиной). Глубина Quick / Standard / Deep по риску.
3. Security-ревью, которое блокирует мёрж, пока есть открытые находки.
4. Блокирующие lint, типы, тесты, сборка. В шаблоне PR — **Testing**, **Risk**, **How to revert**.
5. Одобрение людей по риску: низкий (документация, тексты, фичи за флагом) — 0; средний (обычные изменения, кэш, автообновление, системные промпты) — 1; высокий — 2. Уровень задаёт изменение, а не автор. **Одобрение агента не заменяет человеческое**; одобрение привязано к коммиту и сбрасывается при новых коммитах. Кто попросил агента сделать изменение — тот за него отвечает.
6. Merge queue, feature flags, сначала внутреннее использование, поэтапный релиз.
7. Быстрое обнаружение и откат в один шаг.

## Что остаётся человеку (пользователю)
- Решать, **стоит ли это вообще делать**: направление, вкус, объём.
- Смотреть рискованные пути: биллинг, авторизация, CI, релиз.
- Архитектура, которую будут копировать.
- **Читать доказательства**: вывод тестов, скриншоты, находки ревью.
- Отвечать за результат: «ты смёржил — ты отвечаешь».

## Для настройки репозитория (рекомендации статьи)
- Короткий CLAUDE.md с командами проверки + хуки на форматтер и линтер.
- REVIEW.md: как выглядит провал в этом репо, лимит nit, пути, которые пропускать, требование «файл и строка как доказательство», сводка с количеством находок.
- AI-ревьюер (Code Review for Claude Code или Claude Code GitHub Action), автоматическое security-ревью, все треды закрыты до мержа.
- CODEOWNERS и branch protection на auth, биллинг, CI, релизы, установщики.
- Инциденты и откаты — в набор проверок для ревьюера.
